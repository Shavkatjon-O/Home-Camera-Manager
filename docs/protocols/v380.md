# V380 LAN protocol

This document specifies the local network protocol of V380 cameras as far as a client needs it to find a camera, log in, receive its main or sub stream with sound, and send PTZ, light, siren and picture commands. It is written so that a client, a stream adapter and a device simulator can be built from it alone.

## 1. Scope and status

The protocol runs over TCP between a client and the camera, plus a UDP broadcast for discovery. Cameras can also be reached through the vendor's relay service, which uses different request layouts; this document does not cover it.

Every statement carries one of three status words where it matters:

| Status | Meaning |
|---|---|
| verified | seen working on the project's own cameras: two dual-lens 4G PTZ models, one reporting device version 31 and one device version 32 |
| consistent | the existing client implementations agree on it, but it has not been seen on the project's cameras |
| unverified | a single source, an inference, or a guessed meaning; treat it as an assumption and test it before relying on it |

A statement without a status word is a definition made by this document, such as a recommended timeout. Section 18 lists every unverified item in one place.

## 2. Conventions

- All integers are little-endian. u8, u16, u32 and u64 are unsigned integers of 1, 2, 4 and 8 bytes; i32 is a signed 32-bit integer in two's complement.
- Offsets are zero-based byte offsets from the start of the message. Many fields sit at unaligned offsets, such as a u32 at offset 13; a client must read and write them byte by byte.
- Every request is a fixed-size record. Bytes that this document does not name are zero.
- Text fields are ASCII, written from the start of the field and padded with zero bytes. A value longer than the field is truncated.
- The device id is the camera's decimal number shown on its label and in the vendor app. It fits a u32.
- The device version is the u8 the camera returns in its login reply (section 5.3). The communication version is the u16 it returns in its stream login reply (section 6.2). They select the media encryption (sections 9 and 15).
- Hex dumps show offsets in hex and bytes in hex. Lines that hold only zero bytes are left out of dumps of fixed-size records.

## 3. Discovery on the LAN

Discovery finds cameras on the same broadcast domain and returns their address, MAC address and device id (consistent; not confirmed on the project's cameras).

1. The client opens a UDP socket bound to port 10009 on all interfaces, with address reuse and broadcast enabled.
2. It sends the 15 ASCII bytes NVDEVSEARCH^100, with no terminator, to port 10008 of the limited broadcast address 255.255.255.255. A client on a host with several interfaces should also send to each interface's directed broadcast address.
3. It listens on its socket for replies for 250 to 300 ms, then repeats from step 2, five times in all.
4. A reply is an ASCII text of fields separated by the caret character. It is valid when it has at least 13 fields and field 0 is NVDEVRESULT.
5. Duplicate replies are collapsed by MAC address, compared without regard to letter case, or by device id when the MAC field is empty.

| Field | Meaning |
|---|---|
| 0 | NVDEVRESULT |
| 1 | unknown |
| 2 | MAC address, as text such as AA:BB:CC:DD:EE:FF |
| 3 | IPv4 address of the camera, as dotted text |
| 4 | subnet mask, as dotted text |
| 5 | default gateway, as dotted text |
| 6 to 11 | unknown |
| 12 | device id, as decimal text |
| 13 and later | unknown |

The client takes the address from field 3, not from the datagram's source address, and trims spaces from fields. Whether a camera answers to the sender's port or always to port 10009 is unverified; binding the sender to 10009 covers both. Discovery is the way to find a camera that has moved to another address: the client searches and keeps the entry whose device id matches.

A camera that does not answer, or one behind a router, cannot be found this way, so a client must also accept a camera given by address alone.

## 4. Connections and ports

- The camera listens on TCP port 8800 by default (verified). The port is configurable on the client, because a camera may be reached through port forwarding.
- One version-31 camera of the project exposes only TCP ports 8800 and 9800 (verified). The purpose of port 9800 is unknown.
- A session uses two TCP connections to the same address and port, opened one after the other (verified):
  1. the login connection carries the login request and reply (section 5) and is then closed by the client;
  2. the stream connection carries the stream login (section 6), the start request (section 7), then media from the camera (section 8) and control commands from the client (section 11) until either side closes it.
- The stream login must not be sent on the login connection; both existing clients open a new connection (consistent). Whether a camera would accept it on the login connection is unverified.
- Recommended socket settings for the stream connection: TCP_NODELAY on, a receive buffer of 128 KiB and a send buffer of 64 KiB. A main-stream key frame of these cameras spans many fragments and arrives in a burst.
- Connect timeout: 5 s per connection.
- Cameras restart or drop sessions under load (verified). A client keeps one stream session per camera and shares it between consumers instead of opening one per viewer. How many concurrent sessions a camera accepts, and whether it serves a main and a sub stream to two sessions at the same time, is unverified.

## 5. Login

### 5.1 Request, command 1167

The client sends one 520-byte record on the login connection.

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 1167, the login command |
| 4 | u32 | 120 (meaning unknown; constant) |
| 8 | u8 | 31 (meaning unknown, possibly the client's protocol version; constant) |
| 9 | u32 | 1 (meaning unknown; constant) |
| 13 | u32 | device id |
| 17 | 32 bytes | zero |
| 49 | 32 bytes | user name, ASCII, zero padded; the cameras use admin |
| 81 | 64 bytes | encrypted password field, section 5.2 |
| 145 | 375 bytes | zero |

The constants 120, 31 and 1 are sent by every known client and accepted by both of the project's cameras (verified); their meaning is unverified.

### 5.2 Password field

The 64-byte password field carries the password encrypted twice with AES-128 in ECB mode without padding (verified).

1. Take the password as ASCII bytes. Truncate it to 48 bytes and pad it with zero bytes to exactly 48 bytes. This is P, three AES blocks.
2. Encrypt P with the fixed key K1, which is the 16 ASCII bytes macrovideo+*#!^@ (hex 6d 61 63 72 6f 76 69 64 65 6f 2b 2a 23 21 5e 40). The result is C1, 48 bytes.
3. Choose a fresh random key R of 16 bytes, each byte an ASCII letter or digit (A to Z, a to z, 0 to 9), chosen uniformly from a cryptographically strong source.
4. Encrypt C1 with R. The result is C2, 48 bytes.
5. The field is R followed by C2: bytes 0 to 15 are R, bytes 16 to 63 are C2.

The camera recovers the password by decrypting C2 with R and then with K1. Every block is encrypted on its own, so an all-zero block of P always gives the same C1 block; the test vectors show this.

Every known client draws R from letters and digits only; whether a camera accepts other bytes in R is unverified, so a client must keep to letters and digits. How a camera treats a password outside printable ASCII or longer than 48 bytes is unverified. A client therefore refuses a password that holds any character outside printable ASCII (0x20 to 0x7e) before it connects, and reports it as a refusal; it never substitutes, drops or transliterates characters. A password longer than 48 bytes is truncated as step 1 says.

### 5.3 Reply, command 1168

The camera answers with a 256-byte record and the client then closes the login connection. Both of the project's cameras send all 256 bytes (verified: one existing client rejects shorter replies and works with both). A client needs only the first 21 bytes and should accept any reply of at least 21 bytes, reading missing optional fields as zero.

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 1168, the login reply |
| 4 | u32 | result code, table below |
| 8 | u32 | unknown |
| 12 | u8 | device version, such as 31 or 32 |
| 13 | u32 | ticket |
| 17 | u32 | session id |
| 21 | u8 | device type (meaning of values unknown) |
| 22 | u8 | camera type (meaning of values unknown) |
| 23 | u16 | vendor id (meaning of values unknown) |
| 25 | u8 | 1 when a domain name follows, else 0 (unverified) |
| 26 | 32 bytes | domain name, ASCII, zero padded (unverified) |
| 58 | 198 bytes | unknown |

| Result | Meaning |
|---|---|
| 1001 | login accepted (verified) |
| 1011 | unknown user name (consistent) |
| 1012 | wrong password (consistent) |
| 1018 | wrong device id (consistent) |
| any other | login refused for another reason |

The fields at offsets 21 to 57 are read by one client only and used for nothing (unverified). The session id is not used on the LAN (verified: the LAN stream login does not carry it).

A reply whose command is not 1168, or that is shorter than 21 bytes, is a protocol error: the client closes the connection and retries later as section 14 describes. A refusal (any result other than 1001) is not retried quickly: a client waits at least 300 s before it logs in again, and logs in at once only when its credentials change. Whether a camera locks out a client after repeated failures is unverified; 300 s keeps a client with a wrong password to twelve attempts an hour.

### 5.4 Media key

When the device version is greater than 30, the media is encrypted with AES-128 under a 16-byte media key derived from the ticket (verified for versions 31 and 32):

| Key bytes | Value |
|---|---|
| 0 to 3 | the ticket as u32, little-endian |
| 4 to 11 | 5c 79 14 2c 46 23 81 61, which is the u64 0x618123462c14795c in little-endian order |
| 12 to 15 | f0 0d 80 82, which is the u32 0x82800df0 in little-endian order |

So the key is the ticket's four bytes followed by the twelve fixed bytes 5c 79 14 2c 46 23 81 61 f0 0d 80 82. The key belongs to the ticket of the login that preceded the stream login.

## 6. Stream login

### 6.1 Request, command 301

The client opens the stream connection and sends one 256-byte record.

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 301, the stream login command |
| 4 | u32 | device id |
| 8 | u32 | 0 |
| 12 | u16 | 20 (meaning unknown; constant) |
| 14 | u32 | ticket from the login reply |
| 18 | u32 | 0 |
| 22 | u32 | sound: 4097 to receive audio, 4096 for video only |
| 26 | u32 | stream: 1 for the main stream (high definition), 0 for the sub stream (standard definition) |
| 30 | 226 bytes | zero |

The sub stream with sound off and the main stream with sound on are both accepted by both cameras (verified). Whether the camera leaves audio out of the stream when the sound field is 4096 is unverified; a client must ignore audio frames it did not ask for.

The project's cameras deliver these streams (verified):

| Camera | Sub stream (0) | Main stream (1) | Frame rate | Key frame interval |
|---|---|---|---|---|
| device version 32 | H.265 640x720 | H.265 2304x2592 | 15 fps | 2 to 3 s |
| device version 31 | H.265 640x720 | H.265 1920x2160 | 15 fps | 2 to 3 s |

### 6.2 Reply, command 401

The camera answers with one record of up to 412 bytes. The project's cameras send a shorter reply (verified), and a client that waits for 412 bytes stalls until the camera drops the idle connection, after which the start request goes to a closed socket and no video arrives (verified). A client therefore reads the reply as section 13 describes: it stops reading when no further byte arrives for 200 to 300 ms after the first byte. A reply of 32 bytes is the reported short size (unverified as the only size).

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 401, the stream login reply |
| 4 | i32 | result: -11 and -12 mean refused (consistent); every other value is treated as accepted by every known client. The value on success is not recorded (unverified); existing test material uses 1001 |
| 8 | u16 | communication version |
| 10 | u32 | picture width (unverified) |
| 14 | u32 | picture height (unverified) |
| 18 | u32 | largest packet size (unverified) |
| 22 | u8 | audio sample rate code (unverified) |
| 23 | u8 | audio sample size (unverified) |
| 24 | u8 | audio channels (unverified) |

Fields beyond the received length are read as zero. A reply shorter than 8 bytes or with another command is a protocol error. The width and height can serve as a fallback picture size when the stream's parameter sets cannot be parsed (section 10.3), and only when both lie between 16 and 8192; the values the project's cameras put there are not recorded (unverified). The meaning of the result codes -11 and -12 is unknown.

## 7. Starting the stream, command 303

After an accepted stream login, the client sends one 256-byte record on the same connection:

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 303, the start command |
| 4 | u16 | 0x3001 (meaning unknown; constant) |
| 6 | 250 bytes | zero |

No reply record is known. The camera starts sending media fragments right away (verified), and the first frame of a session is a key frame (verified).

## 8. Media framing and reassembly

### 8.1 Fragment header

After the start request, the camera sends a continuous sequence of fragments. Each fragment is a 12-byte header followed by its payload (verified).

| Offset | Size | Value |
|---|---|---|
| 0 | u8 | 0x7f, the fragment marker |
| 1 | u8 | frame type, section 8.2 |
| 2 | u8 | unknown; ignored |
| 3 | u16 | number of fragments in this frame, at least 1 |
| 5 | u16 | index of this fragment within its frame, from 0 |
| 7 | u16 | length of this fragment's payload in bytes |
| 9 | 3 bytes | unknown; ignored |

A header is valid when byte 0 is 0x7f, the fragment count is at least 1, the index is less than the count and the length is between 1 and 20000. The bound of 20000 is a sanity limit that every known client applies; the project's cameras never exceed it, since their main streams play through clients that drop larger fragments (verified as an upper bound in practice, unverified as a protocol maximum).

After a valid header the client reads exactly the stated number of payload bytes. TCP may split a header or payload across reads; the client reads until it has all the bytes.

An invalid header means the client has lost its place in the byte stream. Both known clients then read the next 12 bytes as a new header, which only recovers by chance. A conforming client searches instead:

1. It scans forward byte by byte for a 0x7f that starts a valid header.
2. While it searches, a header counts as valid only when its frame type is one of the types of section 8.2: 0x00, 0x01, 0x16, 0x18, 0x1a, 0x28, 0x29 or 0x5b. The marker byte also occurs inside media payloads, and a 0x7f there can begin twelve bytes whose count, index and length look valid; requiring a known type keeps the search from taking such bytes for a header.
3. The search ends at the first header that passes; the client reads its payload and returns to normal reading, in which a valid header of any other type is read and ignored.
4. The client closes the connection and reconnects as section 14 says after 64 consecutive invalid headers that start with 0x7f, or after skipping 64 KiB without a header that passes.
5. It never reads a payload for an invalid header.

Frames that were cut by the loss are dropped by reassembly (section 8.3). A client that renders video may also hold back video after a search until the next key frame, so its decoder never sees a frame whose reference was lost; a stream adapter passes frames on as usual.

### 8.2 Frame types

| Type | Meaning | Status |
|---|---|---|
| 0x00 | H.264 key frame | consistent |
| 0x01 | H.264 non-key frame | consistent |
| 0x28 | H.265 key frame | verified on device versions 31 and 32 |
| 0x29 | H.265 non-key frame | verified on device versions 31 and 32 |
| 0x16 | audio, IMA ADPCM, 8 kHz mono | verified on the device version 32 camera |
| 0x18 | audio, AAC in ADTS frames | verified on the device version 31 camera |
| 0x1a | audio, G.711 A-law, 8 kHz mono | consistent; neither project camera sends it |
| 0x5b | unknown; skipped | unverified; meaning unknown |

The version-31 camera sends only types 0x28, 0x29 and its audio type on the stream connection: no alarms or other records (verified). A fragment with a valid header and any other type is read and ignored. The audio codec follows the camera model, not the device version: the two project cameras use different audio types.

### 8.3 Reassembly

A frame is the concatenation of the payloads of its fragments, in index order. Video frames and audio frames are reassembled independently, with one buffer for video types and one for audio types, because an audio frame may arrive between two fragments of a video frame. Interleaving is supported by both known clients (consistent); whether the cameras interleave is unverified.

For each kind, video or audio:

1. A fragment with index 0 discards any partial frame of that kind and starts a new one with the fragment's count.
2. A fragment with a non-zero index is appended only when its count equals the current frame's count and its index is the next expected index. Otherwise the partial frame is discarded, the fragment too, and a dropped-frame counter is increased. The next frame then starts at its own index 0.
3. When the fragment with index count minus 1 has been appended, the frame is complete.
4. A complete frame shorter than 16 bytes is discarded.

A frame with a missing, repeated or reordered fragment must never be delivered, because a decoder fed a frame with a hole shows corruption until the next key frame.

The dropped-frame counter counts frames, not fragments. It increases by one when rule 2 discards a partial frame, and by one when a fragment with index 0 replaces a partial frame of the same kind that never completed under rule 1. A fragment with a non-zero index that arrives while no frame of its kind is being built is discarded without counting, because the frame it belonged to was already counted or started before the session. A complete frame discarded under rule 4 is not counted as dropped.

### 8.4 Frame header

The first 16 bytes of every complete frame are a frame header; the rest is the frame's media payload (verified for the layout, unverified for the meaning of the fields).

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | frame number (unverified: assumed to count up) |
| 4 | u16 | inner frame type (meaning unknown) |
| 6 | u16 | frame rate in frames per second (unverified) |
| 8 | u64 | timestamp (unverified: assumed milliseconds since the Unix epoch) |
| 16 | rest | media payload, encrypted as section 9 describes |

The header itself is never encrypted. Camera clocks drift and some keep local time under a vendor time zone (verified), so a client must not use the timestamp as a presentation time without checking it. Section 16 says how to time the output.

## 9. Media decryption

### 9.1 When

The media payload, after the 16-byte frame header, is encrypted when the device version from the login reply is greater than 30 (verified for 31 and 32). At device version 30 or lower it is sent in the clear (consistent; unverified on a camera). The cipher is AES-128 in ECB mode without padding, decrypting with the media key of section 5.4. Each 16-byte block is decrypted on its own.

### 9.2 Video, communication version other than 21

Video payloads are encrypted in a pattern of 80-byte periods (verified):

1. Start at offset 0 of the media payload.
2. While at least 64 bytes remain from the current offset, decrypt the 64 bytes at the offset as four AES blocks, then advance the offset by 80.
3. The 16 bytes that follow each decrypted 64-byte run, and any tail shorter than 64 bytes, are not encrypted and stay as they are.

For a payload of n bytes, the decrypted runs start at 0, 80, 160 and so on, as long as the run's end does not pass n. A payload of fewer than 64 bytes is not encrypted at all.

### 9.3 Audio

Audio payloads are encrypted in whole blocks from the start (verified for types 0x16 and 0x18): the first floor(n / 16) times 16 bytes are decrypted as consecutive AES blocks, and the remaining 0 to 15 bytes are sent in the clear. A 263-byte AAC frame therefore has 256 encrypted bytes and a clear tail of 7 bytes.

### 9.4 Communication version 21

When the stream login reply reports communication version 21, video payloads are decrypted like audio, in whole blocks from the start, instead of in the 80-byte pattern; audio is unchanged (consistent; unverified on a camera, and no camera reporting version 21 is known to the project).

## 10. Video payload, codec parameters and Annex-B output

### 10.1 Start code alignment

A decrypted video payload is an H.265 or H.264 access unit in Annex-B byte stream format: NAL units, each preceded by a start code of 00 00 01 or 00 00 00 01. Some firmware puts a few bytes before the first start code (unverified; not seen on the project's cameras). The client aligns each payload:

1. Search for the three bytes 00 00 01 starting at positions 0 to 15 of the payload (the match may start at position 15 at most and must lie inside the payload).
2. If the match starts at position p and p is greater than 0 and the byte at p minus 1 is 00, the start code is four bytes long and begins at p minus 1. Otherwise it begins at p.
3. Drop the bytes before the start code.
4. If there is no match, drop the whole frame.

### 10.2 Codec identification

The frame type tells key frames from other frames. The codec is best taken from the NAL headers of the first key frame rather than from the frame type, because only the H.265 frame types have been seen on the project's cameras.

- H.265: the NAL unit type is bits 1 to 6 of the first NAL header byte, that is (byte0 >> 1) and 0x3f, and the second header byte is 0x01 for the base layer. A key frame carries types 32 (VPS), 33 (SPS) and 34 (PPS) before its slices.
- H.264: the NAL unit type is the low five bits of the first byte, that is byte0 and 0x1f. A key frame carries types 7 (SPS) and 8 (PPS) before its slices.

A key frame whose first NAL units include an H.265 header of type 32, 33 or 34 with 0x01 as second byte is H.265; otherwise one with an H.264 type of 7 or 8 is H.264. The two tests do not collide for the parameter set bytes these streams use. A client reads the NAL units in order and decides at the first one that is a parameter set of either codec.

The first key frame of a session fixes two things for the whole session:

- the codec: from its NAL units, or from its frame type when they carry no parameter set;
- the frame type family: 0x00 and 0x01 for the H.264 family, 0x28 and 0x29 for the H.265 family, from its frame type.

A later video frame whose frame type is of the other family is dropped and counted, and so is a later key frame whose NAL units name the other codec. A frame whose family agrees with the first key frame is kept even if that key frame's type and NAL units disagreed. No camera is known to send frames whose type and NAL units disagree (unverified).

The project's cameras send VPS, SPS and PPS at the start of their key frames (verified), followed by the key picture's slice NAL units.

### 10.3 Picture size

The picture size comes from the H.265 SPS, parsed as ITU-T H.265 section 7.3.2.2 defines: after the two-byte NAL header and after removing emulation prevention bytes (every 03 that follows two zero bytes), read sps_video_parameter_set_id, sps_max_sub_layers_minus1 and sps_temporal_id_nesting_flag, the profile_tier_level structure, sps_seq_parameter_set_id, chroma_format_idc, separate_colour_plane_flag when chroma_format_idc is 3, pic_width_in_luma_samples, pic_height_in_luma_samples, and the conformance window. The size is the coded size minus SubWidthC times (left plus right offset) and SubHeightC times (top plus bottom offset), where SubWidthC is 2 for chroma formats 1 and 2 and 1 otherwise, and SubHeightC is 2 for chroma format 1 and 1 otherwise. For H.264 the size comes from its SPS in the same way, or from the stream login reply as a fallback.

The project's cameras use 4:2:0 chroma and no conformance window (verified for the three SPS in section 17.9).

### 10.4 The reorder declaration

The H.265 SPS of both project cameras declares sps_max_num_reorder_pics = 1, although the streams never reorder pictures (verified). A decoder that honours the declaration holds every picture back by one frame. On a live-view client of the project, rewriting the field to 0 cut the decode delay from 70 to 94 ms to about 1 ms (verified).

A client that renders live video should rewrite the declaration in every key frame's SPS before passing it to its decoder; a stream adapter whose consumers buffer anyway may pass the SPS through unchanged. The rewrite is:

1. Remove emulation prevention bytes from the SPS NAL unit, giving the RBSP.
2. Parse the RBSP as section 10.3 does, then continue past bit_depth_luma_minus8, bit_depth_chroma_minus8, log2_max_pic_order_cnt_lsb_minus4 and sps_sub_layer_ordering_info_present_flag.
3. For each signalled sub-layer (all sub-layers from 0 when the flag is 1, only the highest when it is 0), read sps_max_dec_pic_buffering_minus1, then note the bit position and length of sps_max_num_reorder_pics, then read sps_max_latency_increase_plus1.
4. If every sps_max_num_reorder_pics is already 0, leave the SPS unchanged.
5. Otherwise build a new bit string: copy all bits before each noted field, write the Exp-Golomb code of 0 (the single bit 1) in place of the field, and copy the bits after it, up to but not including the RBSP stop bit (the last 1 bit of the RBSP).
6. Append the stop bit 1 and zero bits up to the next byte boundary.
7. Insert emulation prevention bytes again: wherever two zero bytes would be followed by a byte of value 0 to 3, insert 03 after the two zero bytes.
8. Replace the SPS NAL unit in the access unit with the result, keeping its start code.

The rewrite is valid only for streams without reordering, which holds for the project's cameras. A client must not apply it to a stream that uses B-frames. sps_max_dec_pic_buffering and every other field stay as they are.

### 10.5 Picture layout of dual-lens models

The project's dual-lens cameras send one picture with both lenses stacked (verified): the top half is lens 1, the fixed lens, and the bottom half is lens 2, the lens that moves with PTZ. Each half has a 16:9 aspect, such as 640x360 in the 640x720 sub stream. A client that shows or analyses a single lens crops the half it needs; the protocol carries no lens metadata.

## 11. Control commands

### 11.1 Transport

Control commands are 16-byte records that the client writes on the stream connection while media is flowing (verified for PTZ). The client serialises its writes, so that two records never interleave. No reply to a control command is known (consistent); the client does not wait for one.

When a stream session of the camera is open, commands go on that session. A client that must send a command while no stream session of the camera is open opens a short control session:

1. a login and a stream login for the sub stream without sound (stream 0, sound 4096), then the start request, as for any session;
2. it reads and discards the media for as long as the session lasts, so the camera keeps sending;
3. it writes the command, and further commands while the session is open;
4. it closes the session 30 s after the last command, or once a siren it keeps sounding has ended, whichever is later, sending a stop first while a move runs.

Whether a camera accepts a short control session while another session streams from it, and how many sessions it accepts at all, is unverified (section 4). A client therefore never opens a short control session when it can reach the stream session that is already open, for example through the process that holds it.

### 11.2 PTZ

| Offset | Size | Value |
|---|---|---|
| 0 | u32 | 0xaa (170), the PTZ command |
| 4 | u16 | 1000 (meaning unknown, possibly a speed; constant) |
| 6 | u16 | 1000 (meaning unknown, possibly a speed; constant) |
| 8 | u16 | pan: 1000 none, 1001 left, 1002 right |
| 10 | u16 | tilt: 1000 none, 1003 up, 1004 down |
| 12 | u16 | 0 |
| 14 | u16 | 1 |

| Move | Bytes |
|---|---|
| left | aa 00 00 00 e8 03 e8 03 e9 03 e8 03 00 00 01 00 |
| right | aa 00 00 00 e8 03 e8 03 ea 03 e8 03 00 00 01 00 |
| up | aa 00 00 00 e8 03 e8 03 e8 03 eb 03 00 00 01 00 |
| down | aa 00 00 00 e8 03 e8 03 e8 03 ec 03 00 00 01 00 |
| stop | aa 00 00 00 e8 03 e8 03 e8 03 e8 03 00 00 01 00 |

A move command starts a motion that lasts until a stop command; the existing clients rely on this, one holding a move for as long as a remote key is held and one sending a stop after a timed move (consistent). Timed moves and stops sent this way turn the version-31 camera and bring it back when retraced (verified). How far a camera turns per second is not measured. The client therefore sends a stop after every move: when the user releases the control, when a timed move ends, when the view changes and before the client closes a session while a move is running. Diagonal moves, with both pan and tilt set, are unverified; a client sends one axis at a time. No zoom, focus or preset command is known for this protocol.

A client may also stop a move by itself after a maximum duration, as a guard against a stop that never comes, such as a release that is lost. Every move record restarts the duration, so a control that keeps renewing its move keeps moving. The recommended maximum is 30 s; how far a camera turns in that time is not measured (unverified).

### 11.3 Light, siren and picture

These records are four u32 fields: the command code, a value, a second value and zero.

| Command | Code | Value | Second value | Bytes |
|---|---|---|---|---|
| light on | 0xc4 | 1001 | 256 | c4 00 00 00 e9 03 00 00 00 01 00 00 00 00 00 00 |

## 12. Audio payloads

The decrypted audio payload depends on the frame type:

- 0x1a: G.711 A-law samples, 8 kHz, mono, one byte per sample (consistent).
- 0x16: one IMA ADPCM block per frame, 8 kHz, mono (verified on the version-32 camera). The block has a 4-byte header: the first sample as i16, the step index as u8 (0 to 88), and one reserved byte. The remaining bytes hold 4-bit codes, the low nibble first, each decoded with the standard IMA ADPCM step and index tables. A 256-byte block decodes to 505 samples: the header sample and two per remaining byte. 256 bytes is the block size the project's client handles (unverified as the only size).
- 0x18: one AAC frame in ADTS format per frame (verified on the version-31 camera). The version-31 camera sends AAC LC, 8 kHz, mono, in ADTS frames without CRC whose header starts ff f9 6c 40, with a frame length of 263 bytes including the 7-byte header (verified). Section 17.10 decodes that header.

## 13. Reading replies, keepalive and timeouts

Control-plane replies have no length field, so a client reads them with a deadline and an idle gap:

1. Read until the expected maximum size has arrived (256 bytes for the login reply, 412 for the stream login reply), or
2. until 5 s have passed without the first byte, which is a timeout, or
3. until 200 to 300 ms have passed without a further byte after at least one byte has arrived, which ends the reply.

The idle gap is safe because the camera sends nothing else on the connection until the client's next request.

No keepalive message is known (consistent). After the start request, the client sends nothing but control commands, and clients that do so serve the project's cameras around the clock (verified). Whether a camera ends a session after a fixed time, which the reconnect rules of section 14 would hide, is unverified.

| Timer | Value |
|---|---|
| TCP connect, each connection | 5 s |
| first byte of a reply | 5 s |
| idle gap ending a reply | 200 to 300 ms |
| media silence on the stream connection before the session counts as lost | 15 s |

## 14. Errors and reconnects

| Condition | Client behaviour |
|---|---|
| connect fails or times out | the camera is unreachable; retry with back-off; a client that knows the device id may run discovery once to find a new address |
| login reply missing, short or with another command | protocol error; close and retry with back-off |
| login result other than 1001, or a password outside printable ASCII | refusal; report the reason from the table in section 5.3; retry after at least 300 s, or at once when the credentials change |
| stream login reply missing, shorter than 8 bytes or with another command | protocol error; close and retry with back-off |
| stream login result -11 or -12 | refusal; close and retry with back-off |
| invalid fragment header | lost framing; search for the next valid header, or reconnect after 64 invalid headers or 64 KiB, as section 8.1 says |
| 15 s without media bytes | session lost; close and reconnect |
| camera closes the stream connection | session lost; reconnect |
| frame with a missing fragment | drop it and count it; keep the session |
| video frame without a start code in its first 16 bytes | drop it; keep the session |
| video frame of the other codec family, or key frame naming the other codec | drop it and count it; keep the session (section 10.2) |
| move without a stop for the maximum move duration | send a stop (section 11.2) |

Each reconnect repeats the whole sequence: login, stream login with the new ticket, start. One known client reuses the previous ticket for a new stream login without logging in again; whether cameras accept that is unverified, so a conforming client logs in again.

A reasonable back-off is 1, 2, 5 and 10 s, then every 30 s. A successful session that delivers media resets the back-off. When the client's network comes back after a loss, it reconnects at once.

## 16. What a correct implementation outputs

A client or stream adapter built from this document produces, per session:

- Video: one H.265 or H.264 elementary stream in Annex-B format. It is the sequence of decrypted, aligned video payloads (sections 9 and 10.1) in arrival order, concatenated without changes, starting with the first key frame; frames before the first key frame are dropped. The one change allowed is at the start of an access unit: a stream adapter may give an access unit whose first start code is the three bytes 00 00 01 a four-byte start code 00 00 00 01, which Annex B requires before the first NAL unit of an access unit and which consumers that detect the format from its first bytes expect. Every key frame keeps its in-band parameter sets, so a consumer can join at any key frame. The output is either H.265 or H.264 for the whole session, as section 10.2 identifies it; a consumer that needs one codec must not receive the other.
- Audio, when requested: a separate elementary stream in the format the frame type gives: A-law bytes at 8 kHz mono for 0x1a; 16-bit little-endian PCM at 8 kHz mono decoded from the IMA ADPCM blocks for 0x16; the ADTS frames as received for 0x18, with the AAC configuration taken from the ADTS header (section 17.10).
- Session facts: device version, communication version, codec, picture size from the SPS, frame rate, and the audio format once the first audio frame has arrived.

Rules for the output:

- Pictures are in decode order and the streams of the project's cameras need no reordering, so presentation order equals arrival order.
- Timing comes from the client's clock at arrival, or from the frame rate when a steady clock is needed, not from the camera's timestamp (section 8.4).
- An audio track is announced only after the first audio frame of a known type has arrived. A camera that is asked for sound may still send none in a format the consumer expects, and a consumer that waits for an announced track that never arrives can stall the whole stream (verified with consumers that expected A-law from these cameras).
- A change of parameter sets at a key frame, for example after a switch between main and sub stream, is passed through in-band; a consumer that configures a decoder from the first key frame must reconfigure.
- The low-latency SPS rewrite of section 10.4 is applied only where a decoder renders live video, and then to every key frame.
- Lost or damaged frames are dropped, never repaired; the next key frame restores the picture.

## 19. Building a device simulator

A simulator lets the client, the adapter and the development kit run without a camera. It plays the camera's side of sections 3 to 13 and is driven by a small configuration: device id, user, password, device version, communication version, ticket source, stream source per stream value, audio type and fault switches.

1. Discovery: listen on UDP port 10008. For a datagram whose text is NVDEVSEARCH^100, answer the sender with NVDEVRESULT^1^ followed by the MAC, address, mask and gateway, six placeholder fields and the device id, all separated by carets, with one trailing field.
2. Login: listen on TCP port 8800. On a connection, read exactly 520 bytes. Check the command and the constants, the device id at offset 13 and the user name at offset 49. Recover the password by decrypting bytes 97 to 144 with bytes 81 to 96 as key and then with the fixed key K1, and compare it, zero padded to 48 bytes, with the configured password. Answer with a 256-byte reply: result 1001 and a fresh random ticket on success, otherwise 1011, 1012 or 1018. Close the connection after the client closes it or after a short delay.
3. Stream login: on the next connection, read exactly 256 bytes, check the command, the device id and that the ticket at offset 14 is one the simulator issued, and note the sound and stream values. Answer with a 32-byte reply by default: result 1001, the configured communication version and the picture size of the selected stream. A switch sends the full 412 bytes instead, and another answers -11.
4. Start: wait for exactly 256 bytes holding command 303, then begin streaming. Sending nothing before the start request matters, because clients end a reply on an idle gap.
5. Media: read the selected stream from an H.265 or H.264 Annex-B elementary stream file without B-frames, such as a sample video converted with a tool that repeats the parameter sets before every key frame, and split it into access units:
   - A new access unit starts at an H.265 VCL NAL unit (types 0 to 31) whose first_slice_segment_in_pic_flag is 1, which is the top bit of the byte after the two-byte NAL header, or at an H.264 slice (types 1 to 5) whose first_mb_in_slice is 0, which makes the top bit of the byte after the one-byte NAL header 1.
   - A further VCL NAL unit whose flag is 0 belongs to the current access unit.
   - NAL units that are not VCL and come before a picture, such as parameter sets, access unit delimiters and prefix SEI, belong to the access unit of the picture that follows them.
   - H.265 suffix SEI (type 40) and filler data (type 38) belong to the picture before them.
   - An access unit is a key access unit when it holds an H.265 IRAP picture (types 16 to 23) or an H.264 IDR slice (type 5).
   - The file is served from its first key access unit, and every loop starts at that access unit again.

   For each access unit, build the 16-byte frame header (counting frame number, frame rate, wall-clock milliseconds), encrypt the payload according to the device and communication versions and the key from the ticket, split the frame into fragments of at most a configured size such as 8000 bytes, and send them at the stream's frame rate. Loop the file, starting each loop with a key frame.
6. Audio: when the client asked for sound, send audio frames of the configured type between video frames, for example one 256-byte ADPCM block every 63 ms (505 samples at 8 kHz), encrypted in whole blocks; with a switch, send audio between two fragments of a video frame.
7. Controls: read 16-byte records on the stream connection at any time, log them, and keep a simulated pan and tilt position that moves while a move is active and stops on stop. A test can then assert that every move was followed by a stop.
8. Faults, each behind a switch: refused login codes; a stream login refusal; a short reply that arrives in two TCP segments; silence longer than 15 s; closing the connection in the middle of a frame; a missing or repeated fragment; a fragment count that changes within a frame; an invalid header; an unknown frame type; bytes before the start code; device version 30 with clear media; communication version 21; H.264 frames; a change of parameter sets at a key frame; dropping the session when a second session opens.
9. Determinism: a mode that serves exactly the transcript of section 17.8 with ticket 0x0badf00d lets a test compare a client's output byte for byte with the hashes given there.

A conformance suite runs every client and adapter against the simulator with each fault switch and checks the outputs of section 16: an Annex-B stream that starts with a key frame and contains only complete frames, audio announced only once it arrives, a stop after every move, and reconnects that follow section 14.
